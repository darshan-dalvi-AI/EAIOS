Document 01

Product Requirements

What EAIOS is, who it serves, the problem it removes, and the measurable bar it must clear to be considered done.

Status · Shipped v0.4 Multi-tenant SaaS 18 applications 9 AI agents 94 automated tests

1.1 Problem statement

Mid-sized organisations of 50–500 people accumulate their operating knowledge in files: HR policies in PDFs, contracts in Word, financials in spreadsheets, runbooks in slide decks. Finding an answer means knowing which file holds it and who has it. New joiners interrupt seniors; seniors repeat themselves; decisions get made on stale documents.

Public AI assistants cannot solve this — they have never seen the company's files, and pasting confidential documents into a consumer chatbot is unacceptable. Enterprise AI platforms that can solve it are priced and scoped for organisations ten times larger.

The gap: companies with enterprise knowledge problems but without enterprise budgets. They need a private assistant that has genuinely read their own documents, cites its sources, and can be run on a single server or entirely offline.

1.2 Product vision

EAIOS is an enterprise AI operating system: a company's private, cited, auditable AI, presented as a full desktop operating system inside the browser. Any company creates its own isolated workspace in seconds; one deployment serves them all.

Grounded

Answers from your files

Hybrid retrieval over the company's own documents, never the open internet unless asked.

Cited

Every claim traceable

Each answer carries source chips, a relevance meter and a confidence score.

Isolated

One workspace per company

Tenant separation enforced in the data layer, not left to individual queries.

Audited

Append-only trail

Logins, uploads, deletions and every access to personal data are recorded.

Resilient

Never a dead end

If the backend or the model provider fails, the interface degrades instead of breaking.

Portable

Cloud or fully offline

Hosted deployment, Docker, Kubernetes, or local models with no API keys at all.

1.6 Non-functional requirements

Performance

98 requests/second, 0 errors

Measured at 100 concurrent users on a single worker: p50 754 ms, p95 2.1 s. Load testing exposed a real connection-pool exhaustion at ~60 users, which was fixed rather than tuned away.

Security

Isolation that cannot be forgotten

PBKDF2 password hashing, HS256 tokens, role guards, per-user and per-IP rate limits, SELECT-only SQL, and tenant scoping enforced by the data layer itself.

Reliability

Degrade, never break

If the backend dies mid-session the interface switches to demo data and polls for recovery. If the model provider fails, a deterministic engine answers instead.

Portability

Zero mandatory dependencies

Runs with SQLite, an in-memory vector store and a local extractive engine — no Docker, no GPU, no API key. Each of those swaps to Postgres, Qdrant and a hosted model by changing one variable.

Accessibility

Reachable by keyboard and touch

Labelled controls, visible focus, a command palette for keyboard users, 40 px touch targets and a reduced-motion mode that disables every animation.

Observability

Nothing is a mystery

Every request records a span waterfall with per-agent timings, viewable in the Traces app; usage and estimated cost are attributed per user and per model.

1.8 Scope boundaries

  • Document lifecycle: ingest, index, cite, delete
  • Role-based team management
  • Workflow automation and observability
Out of scope

Deliberately not built

  • Training or fine-tuning foundation models
  • Being a general-purpose chatbot about the open web
  • Replacing a document management system or CRM
  • Mobile applications written natively per platform
  • Billing and subscription management

Known limitation, stated honestly: tables extracted from spreadsheets are materialised as physical database tables without a tenant column. 2.1 Guiding constraints

Three constraints drove almost every technical decision:

C1

It must run anywhere

An examiner may run it on a laptop with no internet. Every external service therefore sits behind an interface with a working local fallback.

C2

Isolation must be structural

With many companies on one deployment, "remember to filter by company" is not a security model. Isolation belongs in a layer that cannot be bypassed by forgetting.

C3

It must degrade, not fail

A demo that crashes when the backend or model provider hiccups is worthless. Every failure path has a defined, non-fatal behaviour.

2.5 Load-bearing decisions

Isolation as a session hook, not a query filter

There are 37 query sites. Adding .where(org_id == …) to each one means 37 chances to forget, and every future query is a 38th. Instead, two SQLAlchemy event hooks do it centrally: one rewrites every SELECT to include the caller's workspace, the other stamps every INSERT with it. The request layer sets the workspace once after authentication.

Consequence: features written later inherit isolation automatically. The test suite proves two companies cannot see each other's users, documents, tasks, conversations, search results or graph entities.

A fail-closed guard for raw SQL

The SQL agent executes generated SQL as raw text, which the ORM hook cannot see. It therefore has its own guard: every tenant table is rewritten into an org-scoped subquery, the tenant registry is denied outright, and any statement whose shape cannot be proven safe — aliases, comma joins — is rejected rather than executed. Refusing a valid query is an inconvenience; running an unsafe one is a breach.

Graceful degradation at three levels

  • Model fails → a deterministic extractive engine answers, so a demo never stalls on someone else's outage.
  • Backend dies mid-session → the client detects the network-level failure, switches to demo data, and polls health until it can restore live mode.
  • Render crashes → an error boundary pings health and self-heals into demo mode rather than showing a blank page.

Parallel agents, each with their own database session

The router may dispatch several agents at once. A SQLAlchemy session is not thread-safe, so each parallel agent opens its own session and re-fetches the user, and the active trace context is copied into the thread so the span waterfall stays intact.

UI / UX Design

The design thesis, the system that expresses it, and how the same product becomes a desktop operating system on a laptop and a native-feeling app on a phone.

OS metaphor Aurora design system Dark + light WCAG-checked contrast Reduced-motion safe

3.1 Design thesis

Enterprise AI tools look like a chat box with a sidebar. That framing quietly tells the user "this is one feature". EAIOS is a platform — nineteen cooperating capabilities — so it borrows the one interface metaphor every user already knows for "many capabilities at once": an operating system.

Principle 01

Familiar, not novel-for-its-own-sake

Windows, a taskbar and a command palette need no explanation. The novelty is that an AI platform is shaped this way, not that the controls are unusual.

Principle 02

Show the reasoning

Answers carry citation chips, a confidence score and the plan of agents that ran. Trust comes from visible working, not from a confident tone.

Principle 03

Never a dead end

Every empty state offers the next action; every failure explains itself and keeps the app usable in demo mode.

Principle 04

Motion that means something

Animation communicates state — indexing, streaming, an agent working. Decorative motion is limited to the boot sequence and the landing page.

Principle 05

Density with air

Enterprise data is dense. Generous line-height, restrained borders and one accent colour keep it readable rather than cramped.

Principle 06

Respect the device

A phone is not a small desktop. Below 740 px the metaphor changes shape rather than shrinking.

  • Body — Inter at 13–15 px; optimised for small dense UI.
  • Mono — JetBrains Mono for SQL, traces, IDs and the terminal.
  • Scale — 4 px base unit; radii 8 / 12 / 16 px; one elevation shadow plus one glow for focus.

4.3 Document lifecycle

From a file on a laptop to a citation in an answer, and back out again when it is deleted.

4.4 Question-answering flow

  1. Ask — typed, spoken, or triggered by the wake word.
  2. Route — a semantic router reads the request and selects agents; independent subtasks are marked for parallel execution.
  3. Retrieve — keyword and vector searches run and are fused with reciprocal rank fusion, scoped to the workspace.
  4. Augment — relational questions add knowledge-graph paths; questions naming an extracted table go to the SQL agent instead.
  5. Generate — the model answers strictly from retrieved context, streaming tokens as they arrive.
  6. Attribute — citations, a relevance meter, a confidence score and the agent plan are attached.
  7. Record — a span waterfall, a usage event and any personal-data access are written.

Failure behaviour at each step: router fails → deterministic keyword routing. Retrieval empty → the answer says so rather than inventing. Model fails → extractive engine. SQL fails → the agent reads the error and rewrites its own query, up to twice. Interrupted mid-run → state is checkpointed per conversation and resumes at the failed node.

Backend Schema

Twenty-one tables, one tenant column, and the mechanism that makes that column impossible to forget.

21 tables 20 tenant-scoped PostgreSQL / SQLite RLS closed

5.1 The organising idea

Every domain table carries org_id. That single column is the entire multi-tenancy model — and the reason it is safe is that no application code is trusted to apply it.

Why nullable: org_id permits NULL deliberately, so an unscoped system insert produces a row that belongs to nobody rather than raising an error. A boot-time migration then adopts any legacy NULL rows into the default workspace — because a user with no workspace would receive no filter at all, which is precisely the leak this design exists to prevent.

Uniqueness is per-workspace, not global. Entity keys and custom-agent slugs originally carried global unique constraints. Under multi-tenancy that would let one company's data block another's — two customers cannot both have an entity called "Acme". The constraints were reduced to indexes; identity is the pair (workspace, key).

5.3 Indexing and integrity

  • org_id is indexed on all twenty tenant tables — it appears in the WHERE clause of virtually every query.
  • Foreign keys mirror the deletion order: chunks → documents, messages → conversations, mentions → entities.
  • Connection pool sized from load testing: 25 connections with 60 overflow. The default 5+10 exhausted at roughly 60 concurrent users — found by measurement, not guesswork.
  • SQLite development mode enables write-ahead logging and a busy timeout so readers never block behind the single writer.

Database surface hardening

The managed Postgres provider publishes every table in the public schema through an automatic REST API. EAIOS never uses that API, so the surface is closed rather than policed: row-level security is enabled with no policies (deny by default), and the API roles' grants are revoked — including through default privileges, so tables created later, such as the dynamic extracted-table set, are never exposed either.

This does not affect the application: it connects as the table owner, which is exempt from row-level security. Isolation between companies remains an application-layer guarantee; the database policy exists purely to shut an unused door.

6.3 Testing strategy

Layer 1

Backend unit & integration — 94 tests

Every route, guard and service. Includes a dedicated isolation suite, a fail-closed SQL-guard suite and database-hardening tests.

Layer 2

Retrieval quality gate

An evaluation set runs in CI with thresholds on hit-rate and mean reciprocal rank. Retrieval regressions fail the build like any other bug.

Layer 3

Headless browser suites

Real user journeys per feature: signup, upload through the file dialog, workspace deletion, two-user video calls, and every app opening without a crash.

Layer 4

Device matrix

iPhone SE, iPhone 14 Pro, iPad mini, iPad Pro and desktop — asserting no horizontal scroll, reachable controls and an unchanged desktop layout.

Layer 5

Load testing

100 concurrent users against the real API. This is what exposed the connection-pool ceiling.

Layer 6

Visual verification

Screenshots are rendered and inspected. Twice, assertions passed while the interface was visibly wrong — only looking caught it.

Practice that repeatedly paid off: when a bug is found, first write the assertion that reproduces it. Every entry in the isolation suite exists because a specific leak was imagined, tested, and closed.

6.5 What comes next

  1. Tenant column on extracted tables — closes the one honest gap in the isolation model.
  2. Billing and plan limits — the schema already carries a plan field; metering already records usage per workspace.
  3. Confidential computing — the design document exists; execution inside a hardware-attested enclave with remote attestation is the natural next security step.
  4. Fine-tuning from feedback — export approved answers, train an adapter, serve it locally.
  5. Collaborative editing — a shared notes surface using conflict-free replicated data types.

Current status: deployed and live, serving isolated workspaces, with the full test suite green. Every requirement marked Shipped in Document 01 was verified on the running system, not only in development.
